== Overview

Zaplie (formerly Zapp.ie) is a Microsoft Teams application that lets teams send
each other Bitcoin micro-payments ("Zaps" of Sats) as recognition and reward.
It combines a conversational Teams bot, a set of React web tabs, and serverless
HTTP endpoints, all backed by an https://lnbits.com/[LNbits] Lightning wallet
and account system. Every Teams user is automatically provisioned with two
LNbits wallets: an *Allowance* wallet (a spending budget; the bot attempts a
one-off grant of `LNBITS_INITIAL_ALLOWANCE` when it is created, and weekly
top-ups come from the LNbits allowance extension, not the bot) and a *Private*
wallet (where received Zaps accumulate).

== Component Design

=== Teams Bot

`src/index.ts` starts an Express server (default port 3978) and wires a
`CloudAdapter` with multi-tenant credentials. All turns pass through
`FetchUserMiddleware`, which resolves the Teams member and calls
`UserService.ensureUserSetup()` — creating the LNbits user (keyed by the AAD
object id stored in an LNbits extra field) and ensuring the Allowance and
Private wallets exist.

`src/teamsBot.ts` extends `TeamsActivityHandler`. Text commands are registered
in a static `SSOCommandMap` keyed by lower-case message text:

[cols="1,2,2"]
|===
| Command | File | Behaviour

| `send zap`
| `src/commands/sendZapCommand.ts`
| Presents an Adaptive Card (schema 1.5) with a multi-select recipient picker, message, and amount (1–10,000); on submit, pays each recipient and updates the card in place with results and remaining balance

| `show my balance`
| `src/commands/showMyBalanceCommand.ts`
| Lists the user's LNbits wallets with balances (msat/1000)

| `show leaderboard`
| `src/commands/showLeaderboardCommand.ts`
| Ranks users by Private wallet balance in an Adaptive Card

|===

`withdraw my zaps` is implemented as a stub in
`src/commands/withdrawFundsCommand.ts` but is deliberately *not* registered in
`SSOCommandMap` and not listed in the Teams manifests, so the bot never
advertises a command that cannot complete. See issue #293.

The bot also implements Teams SSO handlers (`handleTeamsSigninVerifyState`,
`handleTeamsSigninTokenExchange`). Conversation and user state use in-memory
`MemoryStorage`.

=== LNbits Integration

Three server-side clients speak to the LNbits REST API:

- `src/services/lnbitsService.ts` — bot-side (~20 exported helpers). Auth is
  either an `X-Api-Key` header (admin or wallet invoice key) or a Bearer token
  obtained from `POST /api/v1/auth` (cached at module level with concurrent
  request de-duplication). Uses the core API (`/api/v1/wallet`, `/payments`,
  `/wallets/{id}`) and the core Users API (`/users/api/v1/user`,
  `/users/api/v1/user/{id}/wallet`). Attempts a one-off grant of
  `LNBITS_INITIAL_ALLOWANCE` to a new user's Allowance wallet (`topUpWallet`,
  called from `UserService`); the grant is skipped when the setting is missing
  or not a positive integer, and a failed LNbits request is logged rather than
  retried. Recurring replenishment is not bot code (see Design Decisions).
- `tabs/backend/lnbitsGatewayService.js` — authenticated Express gateway for
  the tabs. It keeps the LNbits service account, admin key, invoice keys, and
  wallet admin keys in the Node process. The React client
  (`tabs/src/services/lnbits/`, split per concern into `gateway`, `cache`,
  `users`, `wallets`, `payments`, `rewards`) calls only same-origin
  `/api/lnbits/*` routes with a verified Entra ID token. Wallet routes resolve
  the wallet through the caller's own LNbits user, so a wallet id on its own
  grants neither reads nor writes. Four reads are deliberately tenant-wide
  because the product is built on them: the user directory, the wallet list with
  balances (leaderboard), the aggregate payment feed, and per-wallet payment
  history, which the team feed and the transaction log read across every
  teammate.
- `functions/services/lnbitsService.ts` — request-scoped variant; the LNbits
  base URL and credentials arrive with each HTTP request.

=== Bot Zap Submission Ledger

Before resolving a recipient or calling LNbits, the bot durably acquires one
recipient slot in `${ZAPLIE_DATA_DIR}/bot-zap-ledger.json`. The slot key is a
SHA-256 digest over the Teams tenant, conversation, card activity, recipient,
and `submitZaps` action. Those Teams identifiers are never stored in plaintext;
records contain only the digest, state, timestamp, and, for a confirmed
payment, its bounded payment hash. Wallet objects and wallet keys are not
persisted.

The first submit writes `processing` before any LNbits payment can begin. A
confirmed payment becomes `paid`; a failure after the outgoing payment request
becomes `unknown`. A failure known to occur before that request removes the
`processing` record so the recipient can be tried again. `processing`,
`unknown`, and `paid` records have no time-to-live: all survive restart, and a
duplicate submit is blocked without another LNbits payment. Operators may
repair an uncertain record only after reconciling it against the LNbits ledger.

Every state transition takes the exclusive `bot-zap-ledger.json.lock` lock,
with an owner token and a five-second timeout, so processes sharing the same
durable directory cannot acquire the same recipient concurrently. Reads
(`get`/`getMany`) are deliberately lock-free: each write replaces the store with
an atomic same-directory rename, so a reader sees one canonical file or the
next, never a partial write, and card rendering never queues behind the payment
path or a stalled lock. The bot does not automatically delete an old lock
because lock ownership is uncertain: a crash-left lock fails every transition
closed after the five-second timeout until an operator follows the recovery
procedure in `docs/DEPLOYMENT.adoc`. That is a deliberate manual outage in
preference to an eviction rule that could re-enable a payment that already
settled. Writes also sweep this store's own temporary files once they are older
than an hour, so a crash between write and rename cannot accumulate snapshots. Lock,
schema, startup-read, and persistence failures all fail closed. Writes use a
unique mode-`0600` `bot-zap-ledger.json.<pid>.<random>.tmp` file in the same
directory, sync it, and atomically rename it over the canonical store. On
POSIX the containing directory is synced too, so the rename that publishes the
record survives a power loss; a failure to sync fails the write closed.

Every write drops `paid` records older than the retention window (ninety days
by default, `retentionMs`; `0` disables it) so the file cannot grow until a
transition outlasts the lock. `processing` and `unknown` records are never
pruned — they are the ones a human still has to settle. Recording an outcome
LNbits has already decided (`markPaid`, `markUnknown`) waits far longer for the
lock than a submit does, logging every five seconds while it waits: a submit
may fail, but abandoning a settled payment would leave the recipient
`processing` for good.

`ZAPLIE_DATA_DIR` must be an absolute path outside explicit development mode,
including Azure runtimes detected without `NODE_ENV`. `npm run dev` explicitly
uses development mode and falls back to the ignored `.zaplie-data` directory
when no override is configured. This fallback is never selected by a deployed
bot.

=== Web Tabs

Routes (`tabs/src/App.tsx`): `/feed`, `/users`, `/rewards`, `/wallet`,
`/settings` — all wrapped in `RequireAuth` (MSAL `acquireTokenSilent`, redirect
to `/login` on failure) — plus `/login`, `/auth-start`, `/auth-end`. Providers:
`MsalProvider` → `RewardNameProvider` → `PageLayout`.

[cols="1,3"]
|===
| Page | Purpose

| Feed
| Zap activity feed, activity chart, and total-Zaps statistics

| Users
| Directory of users with wallet information

| Rewards
| Rewards carousel / redemption view

| Wallet
| Private and Allowance wallet tabs: balance card, transaction history, allowance status

| Settings
| Administrator setting to rename "Sats" (the reward label)
|===

The reward label is persisted by the Express backend
(`GET/POST /api/reward-name` → `data.json` under `ZAPLIE_DATA_DIR`) and consumed by both
the tabs (`RewardNameContext`) and the bot (`src/services/fetchRewardsName.ts`).

=== Azure Functions

Three anonymous HTTP triggers under `functions/` (compiled to `dist/`):
`getUsers`, `showUsers`, and `sendZap` (invoice-and-pay between two users'
wallets — the automation/Copilot entry point). LNbits credentials are supplied
per-request via HTTP Basic auth plus `siteURL`/`adminkey` query parameters.

== Data and State

[cols="1,2,2"]
|===
| Data | Where it lives | Notes

| Users and wallets
| LNbits (core Users API)
| Keyed by AAD object id in an extra field; one Allowance + one Private wallet per user

| Transactions / Zaps
| LNbits payments ledger
| Queried per wallet for feed, history, and leaderboard. Each zap carries an
  `extra` object `{ tag: 'zap', from, to }` where `from`/`to` are
  `{ id, name, user, displayName }` projections of the wallets, never the
  wallet objects themselves

| Reward label ("Sats")
| `data.json` under `ZAPLIE_DATA_DIR`
| JSON file on the web server; set the directory to `/home/data/zaplie` on Azure

| Portal connections, identities, pending rewards, and server-side credentials
| JSON stores under `ZAPLIE_DATA_DIR`
| Mutable runtime state is outside the immutable application package

| Bot Zap submission records
| `bot-zap-ledger.json` under the bot's `ZAPLIE_DATA_DIR`
| Hashed per-recipient processing, uncertain, and paid barriers used to prevent another LNbits payment across retries, restarts, and bot processes

| Bot conversation state
| `MemoryStorage` (in-process)
| Ephemeral — lost on restart, not multi-instance safe

| Zap card payment ledger
| `ZapLedger` (in-process `Map`, `src/services/zapLedger.ts`)
| One payment per card recipient for the life of the process; paid and
  unknown slots never expire. Lost on restart, not multi-instance safe
  (durable ledger tracked in #187)
|===

== Design Decisions

=== Payment metadata is a projection, not the wallet

*Context:* LNbits stores the payment `extra` object as JSON on the payment
row. Anyone holding the receiving wallet's invoice key can read it, and the
portal feed loads it into every browser. Until this decision the bot wrote
the full sender Allowance and receiver Private `Wallet` objects there,
including `adminkey`, `inkey` and `balance_msat`.

*Decision:* Writers build `extra.from` and `extra.to` through
`toPaymentExtraWallet` (`src/services/paymentExtra.ts`), which picks
`id`, `name`, `user` and an optional `displayName` by name and throws when
the wallet is missing. No writer depends on the `Wallet` type for metadata.

*Consequences:* New payments carry no key material. Readers (portal feed,
automation summary, transaction log) already use only those fields.
Payments written before this decision cannot be rewritten through the
LNbits API; rotating the affected wallet keys is an operator decision.

=== LNbits as the wallet backend

*Context:* The system needs per-user custodial Lightning wallets with an
admin API.

*Decision:* Use LNbits with its core Users API rather than building a
ledger.

*Rationale:* Open source, self-hostable, proven Lightning integration, and a
REST API that supports programmatic user/wallet creation and payments.

=== Two wallets per user (Allowance vs Private)

*Context:* Users need both a budget to give from and a balance they have earned.

*Decision:* Provision each user an Allowance wallet (granted
`LNBITS_INITIAL_ALLOWANCE` on a best-effort basis at creation; weekly top-ups
come from the LNbits allowance extension) and a Private wallet (receives
Zaps).

*Rationale:* Cleanly separates "money to give" from "money earned", enabling
leaderboards on Private balances and periodic replenishment without touching
earnings.

=== Scheduled top-ups are not bot code

*Context:* The bot carried a `scheduledTopup()` function that swept every
Allowance wallet into a host wallet and refunded it. Nothing on `main` ever
called it: the node-cron job that invoked it on the PR #73 branch was removed
on that branch (59c25967) before the squash merge (82f2fd1b). It read three
settings
(`LNBITS_HOST_WALLET_ID`, `LNBITS_HOST_USER_ID`, `LNBITS_INKEY`) used nowhere
else, and it ran its per-wallet payments in a fire-and-forget loop (PR #242
and PR #310 document the defects).

*Decision:* Remove it, per the Product Owner on PR #242 ("I think
`scheduledTopup` is deadcode if we're going to use the allowance extension for
LNbits?") and PR #310 ("Can still remove the dead code."). Recurring
allowance funding belongs to the LNbits
https://github.com/BenGWeeks/allowance[allowance extension], which pays to a
Lightning address on a schedule, so each Allowance wallet needs a Lightning
address before that can be wired up (tracked separately). The bot only
attempts to fund a wallet once, when it is created: `applyInitialAllowance`
skips the grant when `LNBITS_INITIAL_ALLOWANCE` is missing or not a positive
integer, and `topUpWallet` logs a failed LNbits request instead of retrying,
so user setup never fails on funding and no later balance check enforces it.
Weekly top-ups are the allowance extension's job.

*Consequences:* No scheduler, host wallet or sweep logic lives in the bot.
The leaderboard keeps excluding payments whose memo contains
`Weekly Allowance cleared` so historical sweeps never count as zaps.

=== Teams Toolkit for provisioning

*Context:* The app spans an AAD app registration, a bot registration, an App
Service, and a Teams app manifest.

*Decision:* Drive provisioning and deployment through TeamsFx
(`teamsapp.yml` + `infra/azure.bicep`).

*Rationale:* Single declarative lifecycle for AAD, Bot Service, ARM resources,
and manifest packaging across local/dev environments.

== Known Limitations

- Conversation and user state are in-memory; a restart clears them. Zap
  submission records are the exception: they persist under
  `ZAPLIE_DATA_DIR` so a restart cannot pay a recipient twice.
- The reward-name API is guarded by a placeholder shared secret and a JSON
  file rather than a real datastore.
- The Azure Functions are anonymous at the platform level and receive LNbits
  credentials per request.
- The JSON stores under `ZAPLIE_DATA_DIR` are persistent on a single App
  Service instance but are not a multi-instance transactional datastore.
- The bot's durable ledger depends on a shared, durable filesystem within its
  App Service; it is not a cross-App-Service or cross-region database.
- Recovery of a bot Zap left `processing` or `unknown` requires manual
  reconciliation with the LNbits payment ledger. The application deliberately
  does not guess the payment outcome.
