== Prerequisites

- Node.js 24 (`package.json` `engines`; App Service is pinned to `~24` by
  `infra/azure.bicep` and CI builds on Node 24 — see the MSAL override note in
  README.md)
- Teams Toolkit VS Code extension ≥ 5.0.0 or the TeamsFx CLI (`teamsapp`)
- An M365 tenant with permission to upload custom Teams apps
- An LNbits 1.0+ instance (the shared test instance runs 1.5.6); the core Users
  API replaced the User Manager extension, so no extension is required
- Azure subscription (for dev/prod provisioning)

== Provisioning (Teams Toolkit)

`teamsapp.yml` defines the lifecycle. `teamsapp provision --env dev` performs:

. `aadApp/create` — AAD app registration ("Zapp.ie", single-tenant sign-in
  audience, generates a client secret)
. `cli/runNpmCommand` — `npm run write-env` (copies the LNBITS_*, LEADERBOARD_*
  and URL values into the env file) and `npm run build-manifest` (renders
  `manifest.template.json` → `appPackage/manifest.json` via `build.js`)
. `teamsApp/create` and `botAadApp/create`
. `arm/deploy` — `infra/azure.bicep` with `infra/azure.parameters.json`:
  App Service plan (B1), Windows web app (httpsOnly, alwaysOn,
  `WEBSITE_RUN_FROM_PACKAGE=1`, Node `~24`), app settings (BOT_*, AAD_APP_*,
  `NODE_ENV=production`, `ZAPLIE_DATA_DIR=%HOME%\data\zaplie`),
  and `infra/botRegistration/azurebot.bicep` — Azure Bot Service (F0) with the
  MS Teams channel
. `aadApp/update`, manifest validation, `zipAppPackage`, `teamsApp/update`

== Deploying

=== Bot (Teams Toolkit)

[source,bash]
----
teamsapp auth login azure
teamsapp provision --env dev
teamsapp deploy --env dev      # npm install + build, then zipDeploy to the App Service
teamsapp preview --env dev
----

The bot runs under iisnode on Windows App Service; `web.config` rewrites
static content to `public/` and everything else to `lib/src/index.js`.

=== Local development

[source,bash]
----
devtunnel host -p 3978 --protocol http --allow-anonymous
# set BOT_DOMAIN and BOT_ENDPOINT in env/.env.local, then:
teamsapp provision --env local
teamsapp deploy --env local
teamsapp preview --env local
----

Or press F5 in VS Code ("Debug in Teams (Edge/Chrome)"). The bot itself runs
with `npm run dev` (nodemon + ts-node, inspector on 9239), reading
`.localConfigs` via `npm run dev:teamsfx`. That command explicitly selects
development mode; if `ZAPLIE_DATA_DIR` is omitted, only this mode uses the
ignored `.zaplie-data` fallback.

=== Web tabs (GitHub Actions)

`.github/workflows/Azure_App_Service_zaplie-test.yml` and
`Azure_App_Service_zaplie-prod.yml` trigger on push to `main` (and manually):

. Build job (windows-latest, Node 24): `cd tabs && npm install && npm run build`
  (`CI: false`), scan the sources and the built bundle for LNbits admin
  credentials, drop the mutable backend JSON stores, upload the `tabs` artifact
. Deploy job (ubuntu-latest): `azure/webapps-deploy@v3`

The two workflows authenticate differently today:

Test:: Deploys with federated OIDC — `azure/login` using the repository
secrets `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` and `AZURE_SUBSCRIPTION_ID`
(`id-token: write`), then ensures a deployment slot exists (`pr-<number>` for
pull requests, else `testing`) on app `zaplie-dev` before deploying to it.
Prod:: Deploys to app `zaplie-prod-webapp` with federated OIDC too: the deploy job
runs in the `Prod` environment and `azure/login` takes the `AZURE_CLIENT_ID`,
`AZURE_TENANT_ID` and `AZURE_SUBSCRIPTION_ID` variables from it. They name an app
registration with a federated credential for
`repo:knowall-ai/zaplie-bot:environment:Prod` and Website Contributor on that app
only. No publish profile is needed, so SCM basic auth can stay off.

Note: neither workflow has a bot job — CI deploys only the portal, and it
deploys the whole portal: the React build *and* the Express backend under
`tabs/backend`. The portal App Service must therefore use the startup command
`node backend/server.js` (with `SCM_DO_BUILD_DURING_DEPLOYMENT=false`, since
the artifact arrives prebuilt). The bot deploys separately via
`teamsapp deploy`.

=== The portal on getzapl.ie (/portal/)

The tabs app has a second home: the **Login** button on
https://getzapl.ie opens the same React app at `https://getzapl.ie/portal/`,
served as static files by the website's Azure Static Web App
(`knowall-ai/zaplie-website`, `website/build.mjs` copies the build into
`dist/portal`). Nothing else is deployed there: the Express backend stays on
the portal App Service, and the browser calls it across origins.

The build for that path is the ordinary CRA build with two more settings, both
public values:

[source,bash]
----
cd tabs
PUBLIC_URL=/portal \
REACT_APP_API_BASE_URL=https://<portal App Service host> \
REACT_APP_AAD_CLIENT_ID=... REACT_APP_TENANT_ID=... \
npm run build
----

`PUBLIC_URL` is read once, at build time, by `tabs/src/services/appLocation.ts`:
it becomes the router `basename`, the prefix of the auth routes
(`/portal/auth-start`, `/portal/auth-end`, `/portal/login`) and the MSAL
redirect URI (`https://getzapl.ie/portal`, no trailing slash, like
`TAB_ENDPOINT`). `REACT_APP_API_BASE_URL` prefixes every `/api/...` call;
unset, calls stay same-origin, so the Teams deployment is unchanged.

Before the portal can sign anyone in there, the app registration
(`aad.manifest.json`, single tenant) needs six more single-page application
redirect URIs: `https://getzapl.ie/portal`, `https://getzapl.ie/portal/auth-end`,
`https://getzapl.ie/portal/login`, `https://www.getzapl.ie/portal`,
`https://www.getzapl.ie/portal/auth-end` and
`https://www.getzapl.ie/portal/login`. The `/login` ones are the sign-out
landing: Entra only redirects after sign-out to a registered URI.
The backend already answers cross-origin requests (`cors()` in
`tabs/backend/server.js`); `PORTAL_URL` on the App Service should point at
`https://getzapl.ie/portal` once the GitHub identity and connection redirects
are meant to land there.

People who have never used the bot in Teams have no LNbits user. The portal
provisions one on first sign-in: `POST /api/lnbits/users/me` (the one gateway
route that does not require an existing LNbits user) creates the user, keyed
by the Entra `oid` in `external_id` like the bot does, and its empty
`Allowance` and `Private` wallets. It moves no sats: the opening allowance
(`LNBITS_INITIAL_ALLOWANCE`) remains the bot's doing, so a person set up this
way can receive zaps at once and send them once their Allowance wallet is
funded.

The route serves exactly the people the bot serves. `tabs/backend/memberGate.js`
mirrors `src/services/memberGate.ts`: members of the home tenant are
provisioned; guests and users from other tenants only if listed in
`ZAPLIE_GUEST_ALLOWLIST` (same format, set it on the portal App Service as
well as the bot's); anyone else is refused with 403 and nothing is created.
The portal backend has no Graph access, so membership comes from the verified
idToken: `tid` is the tenant and the optional claim `acct` is the role
(0 member, 1 guest). `aad.manifest.json` requests `acct` in idTokens; until
that is applied to the app registration (`teamsapp provision` outside
production, or *Token configuration* in the Entra portal; see Day One for
production) no token carries it and the route
refuses everyone, by design. People who already have an LNbits user are not
affected: only creation is gated.

=== Persistent application state

The bot keeps its mutable state — the durable Zap ledger
`bot-zap-ledger.json`, the automation reward ledger `bot-reward-ledger.json`
and the reward budget ledger `bot-reward-budget.json` — under
`ZAPLIE_DATA_DIR`. Bicep sets
`ZAPLIE_DATA_DIR=+%HOME%\data\zaplie+` on the App Service it provisions
(Windows: `kind: 'app'`, no `reserved`/`linuxFxVersion`), outside `wwwroot`, so
a clean deployment cannot replace it. App Service passes app settings to the
process verbatim — it does not expand `%VAR%` for an arbitrary setting — so the
bot expands the `%HOME%` token itself in `src/services/dataDir.ts`, from
`process.env.HOME` with a platform default (`+D:\home+` on Windows, `/home`
elsewhere) if it is absent. That resolves to `+D:\home\data\zaplie+` on an
older Windows stamp, `+C:\home\data\zaplie+` on a newer one and
`/home/data/zaplie` on Linux, so the same setting is correct everywhere and no
drive letter is baked in. An absolute literal path still works unchanged. Local development falls
back to the git-ignored `.zaplie-data` directory when the variable is absent;
every deployed (non-development) runtime must set it to an absolute path or
the bot refuses to start.

Never include mutable JSON in a deployment artifact: `.webappignore` excludes
the three ledgers, their `.lock` files, and their `<ledger>.json.<pid>.<random>.tmp`
replacements. The bot creates the data directory with mode `0700` and ledger,
lock, and temporary files with mode `0600` on supporting filesystems.

Back up and restore the data directory as an application-consistent unit:

. Stop or drain every bot process sharing the directory before copying it.
. Copy the canonical `bot-zap-ledger.json`, `bot-reward-ledger.json` and
  `bot-reward-budget.json` together; never copy `.lock` or `.tmp`
  artifacts. Keep backups access-controlled: payment hashes are operational
  metadata, and the reward ledger also holds the GitHub login of each
  rewarded recipient.
. To restore, keep the bot stopped, preserve a copy of the current directory,
  restore the canonical backup into `ZAPLIE_DATA_DIR`, restore restrictive
  permissions, and then start the bot.
. If a restore moves a ledger backward in time, reconcile every potentially
  affected Zap or reward against the LNbits ledger before accepting
  submissions: a reward key missing from a restored file pays again when its
  webhook is redelivered. Never delete or rewrite `processing`, `unknown` or
  `uncertain` records merely to make a retry succeed.

A ledger's `.lock` is only ever held across local file I/O (a read, a JSON
serialise and one synced rename), so a healthy hold lasts milliseconds. A lock
survives only when the process dies holding it, typically an App Service
restart (platform maintenance, scale, `az webapp deploy`, an Always On
recycle) that kills the bot mid-transition. The rule is:

* *At startup* each ledger removes its own `.lock` if it is older than
  `ZAPLIE_LEDGER_STALE_LOCK_MS` (default 30 seconds; `0` turns this off) and
  logs `... was <n>s old at startup and has been removed as crash-left`. A
  younger lock is left alone and logged as
  `... is <n>s old and may belong to a live process; leaving it`. The lock is
  moved aside with a rename and its inode checked on both sides, so a lock a
  live process re-took in the meantime is put back, never deleted. If the
  lock cannot be inspected at all, the bot refuses to start. If recovery logs
  `could not be put back`, the token is in the named `.stale.` file; move it
  back to `.lock` only if no `.lock` exists, then restart.
* *At runtime* nothing is evicted. While `bot-zap-ledger.json.lock` is
  present every zap submission fails, and while `bot-reward-ledger.json.lock`
  or `bot-reward-budget.json.lock` is present every reward request fails,
  after the five-second lock timeout with an error naming this procedure. Each
  timeout is also recorded as a `ledger.lock_timeout` activity (subject
  `ledger-lock`) so an alert can fire on it (see <<Telemetry>>).
* *Records are never cleared automatically.* Recovery frees the lock, not the
  payment: a `processing`, `unknown` or `uncertain` record left by the same
  crash keeps blocking that payment. At startup the zap ledger logs how many
  `processing` or `unknown` records it holds (a count, never the keys); each
  one needs reconciling with LNbits.

Manual recovery, when the startup rule did not apply (the lock was younger
than the threshold at boot, recovery is turned off, or a lock appeared while
the bot was running): restart the bot once more after 30 seconds, or
stop/drain every bot process, inspect the canonical store, reconcile any
`processing`, `unknown` or `uncertain` record with LNbits, and only then
remove the orphaned `.lock` (never the `.json`). Never delete or rewrite a
record merely to make a retry succeed. Store corruption, an unreadable data
directory, or lock acquisition failure prevents payment.

Each ledger sweeps its own `.tmp` files older than an hour once, when the bot
starts, so a crash between writing a temporary and renaming it cannot
accumulate ledger snapshots on the share; nothing younger is touched, because
it may belong to a write in flight.

==== Reconciling the reward ledger

`bot-reward-ledger.json` records one entry per reward key (stored as a
SHA-256 digest, never the raw key): the `Idempotency-Key` sent to
`POST /api/v1/rewards`, or `github:pull_request:<id>:merged` for the signed
GitHub webhook. `paid`
and `pending` entries hold the response a repeat replays and are pruned after
90 days. Two states never expire and always need a person:

* `uncertain`: the payment call to LNbits failed or returned no payment hash,
  so the reward may have been paid. Every redelivery gets a `409`. Search the
  treasury wallet's outgoing payments in LNbits around the entry's `at` time
  (milliseconds since the epoch) for the recipient and amount. If it settled,
  the entry can stay as it is, since the reward is paid. If it did not, stop
  the bot, delete that one entry from `records`, delete the reservation with
  the same digest from `bot-reward-budget.json` (under the period that holds
  it), start the bot, and redeliver the delivery from GitHub (*Settings →
  Webhooks → Recent deliveries → Redeliver*) or resend the API request. When the recipient had not linked GitHub, the uncertain
  call was the portal's pending-reward write instead (the bot logs
  `pending reward write`): look in the portal's `pending-rewards.json` for an
  entry for that GitHub id and amount. If it is there, leave the ledger entry
  as it is; if not, delete the ledger entry and resubmit.
* `processing` that is older than a few minutes: the bot stopped mid-request,
  or the payment settled but the ledger could not record it (the bot logs
  `rewards ledger could not record a settled reward`). Reconcile it the same
  way. Also check the portal's pending rewards for a duplicate entry for the
  recipient: a pending reward is written to the portal before the ledger
  records it.

Edit the file only with every bot process stopped, keep the JSON valid, and
keep a copy of the file you started from. The bot refuses to start on a store
it cannot validate rather than guessing.

==== The reward budget ledger

`bot-reward-budget.json` holds, per budget period (`week:2026-W44` or
`month:2026-10`), one reservation in sats per reward key, using the same digest
as the reward ledger. The period is the one current when the bot processes the
delivery, not the merge time. The bot reserves the amount before paying and
refuses a reward that would take the period over the cap (`402`, nothing
paid). Paid, pending and uncertain rewards keep their reservation; only a failure known to
be before the payment releases it. A reservation that could not be released is
logged (`reward budget could not release an unpaid reward`) and over-counts
the period: it never over-pays. Periods older than about 13 months are pruned.
The cap comes from the portal's reward policy or the `REWARDS_BUDGET_*`
settings; with neither, every reward answers `503`.

== Environment Variables

[cols="2,3,1"]
|===
| Variable | Description | Component

| `BOT_ID`, `BOT_PASSWORD`, `BOT_DOMAIN`
| Bot Framework registration credentials and public domain. `BOT_ID` (the
  Entra application id, a GUID) and `BOT_PASSWORD` are required: the bot
  refuses to start if either is missing or blank, or if `BOT_ID` is not a
  GUID, as it does without `AAD_APP_TENANT_ID`
| Bot

| `AAD_APP_CLIENT_ID`, `AAD_APP_CLIENT_SECRET`, `AAD_APP_TENANT_ID`, `AAD_APP_OAUTH_AUTHORITY_HOST`
| Entra ID app registration for SSO
| Bot

| `LNBITS_NODE_URL`
| Base URL of the LNbits instance
| Bot, Portal backend

| `LNBITS_USERNAME`, `LNBITS_PASSWORD`
| LNbits service-account credentials (`POST /api/v1/auth`) — server-side only,
  never with a `REACT_APP_` prefix
| Bot, Portal backend

| `LNBITS_ADMINKEY`
| LNbits admin API key for wallet operations — server-side only, never with a
  `REACT_APP_` prefix
| Bot, Portal backend

| `LNBITS_INITIAL_ALLOWANCE`
| Sats the bot attempts to grant to each user's Allowance wallet when it is
created. Must be a positive integer; a failed grant is logged, not retried
| Bot

| `LNBITS_POINTS_LABEL`
| Default reward-unit label (renamable in Settings)
| Bot, Tabs

| `LEADERBOARD_WINDOW_DAYS`, `LEADERBOARD_TOP_N`
| `show leaderboard` window in days (default `7` like the portal), a whole
  number from `1` to `365`, and rows shown (default `10`), a whole number from
  `1` to `100`. The assistant's `get_leaderboard` tool uses the same window
  when the user does not name one. A malformed value or one outside its range
  makes the command reply "unavailable" and log the variable name; it is never
  clamped
| Bot

| `ZAP_MAX_RECIPIENTS`
| Most people one zap card may pay (default `3`). A whole number of `1` or
  more; anything else makes the bot refuse to start. The card shows the limit
  and the submit refuses more before reading the ledger or LNbits. Each
  recipient costs four LNbits calls and two ledger writes on the sender's
  turn, which Teams ends after 15 seconds, so raise it only after measuring a
  submit in your tenant; from `4` up the estimated slow case crosses the
  limit. Not declared in `infra/azure.bicep`, whose `appsettings` resource
  replaces the whole collection, so a value set by hand with `az webapp
  config appsettings set` is lost on the next `teamsapp provision`; set it
  again afterwards
| Bot

| `REACT_APP_AAD_CLIENT_ID`, `REACT_APP_TENANT_ID`
| MSAL configuration for the tabs SPA
| Tabs

| `PUBLIC_URL`
| Base path of the tabs build (`/portal` for getzapl.ie/portal/; unset at the
  root). Sets asset paths, the router basename and the MSAL redirect URI
| Tabs (build time)

| `REACT_APP_API_BASE_URL`
| Origin of the Express backend when the tabs are served from another host
  (`https://<portal App Service host>` for getzapl.ie); unset, `/api` calls stay
  same-origin
| Tabs (build time)

| `WEBSITE_URL`, `CONTENT_URL`
| Public URLs substituted into the Teams manifest by `build.js`
| Manifest

| `WEBSITE_API_URL`
| Portal backend API base URL used by the bot; include the `/api` prefix
  (`https://<portal-domain>/api`), routes are appended to it verbatim
| Bot

| `TAB_BACKEND_TOKEN`
| Shared secret the bot presents when calling the portal backend; generate
  with `openssl rand -hex 32` and set the same value on both apps
| Bot, Portal backend

| `GITHUB_WEBHOOK_SECRET`
| Secret GitHub signs webhook deliveries with (`X-Hub-Signature-256`);
  generate with `openssl rand -hex 32` and use the same value in each
  repository webhook. Unset: `POST /api/v1/github/webhook` answers 503
| Bot

| `REWARDS_API_KEY`
| Static API key accepted by the bot's rewards endpoint (in addition to
  portal-managed keys created in Automations). GitHub does not use it
| Bot

| `REWARDS_TREASURY_ADMINKEY`
| Admin key of the LNbits treasury wallet that reward payouts are drawn from
| Bot

| `REWARDS_MAX_AMOUNT_SATS`
| Upper bound in sats for a single automated reward, base plus level bonus
  (default 10000). A malformed value fails closed — reward rules are rejected
  rather than accepted under an unintended ceiling
| Bot, Portal backend

| `REWARDS_BUDGET_PERIOD`, `REWARDS_BUDGET_CAP_SATS`, `REWARDS_BUDGET_TIMEZONE`
| Optional overrides of the portal's reward budget: `week` or `month`, a
  positive whole number of sats per period, and an IANA time zone. Each one
  set wins over the portal's field; with no complete budget in either place
  every reward answers 503. A malformed value fails closed
| Bot

| `ZAP_MAX_AMOUNT_SATS`
| Upper bound in sats for a single person-to-person zap or self-issued invoice
  through the portal's LNbits gateway. Distinct from `REWARDS_MAX_AMOUNT_SATS`,
  which caps automated rewards only, but it inherits it: left unset the zap
  ceiling is whatever `REWARDS_MAX_AMOUNT_SATS` is set to, falling back to
  1000000 only when neither is set. Set it to give zaps a ceiling of their own.
  A malformed value fails closed: the gateway rejects the request with a 503
  rather than falling back to a wider ceiling
| Portal backend

| `ALLOWANCE_FUND_ADMINKEY`
| Admin key of the LNbits wallet the allowance extension pays weekly
  allowances from (the "Fund" wallet on the Zaplie account; never a wallet
  named `Allowance` or `Private`, never a person's). Comma-separated for more
  than one Fund wallet, in order (the extension allows 100 schedules per
  wallet). Only ever sent to the allowance extension's schedule, health and
  `GET /api/v1/wallet` routes the sync uses; never logged, stored or returned.
  Unset: the allowance
  sync can preview pay links only and refuses to apply (503)
| Portal backend

| `ALLOWANCE_MAX_AMOUNT_SATS`
| Upper bound in sats for one person's allowance per period (default 100000).
  A malformed value fails closed
| Portal backend

| `LNBITS_PUBLIC_HOST`
| Public host of LNbits that Lightning addresses are served on (for example
  `bank.knowall.ai`). Defaults to the host of `LNBITS_NODE_URL`. The extension
  pays over public HTTPS, so it must not be an internal address
| Portal backend

| `ALLOWANCE_SYNC_CONCURRENCY`, `ALLOWANCE_PER_WALLET_LIMIT`, `ALLOWANCE_MAX_PEOPLE`
| Optional tuning for the allowance sync: parallel LNbits calls (default 4),
  schedules per Fund wallet (default 100, the extension's limit) and the most
  people one policy may cover (default 1000; more refuses to apply)
| Portal backend

| `ALLOWANCE_SYNC_INTERVAL_MINUTES`
| How often the portal backend runs the allowance sync on its own (default
  360; `0` turns it off; a malformed value also turns it off). It only
  maintains a policy an admin has already previewed and applied, never
  applies over a block such as an underfunded Fund wallet, and applies a
  disabled policy (which only pauses schedules) without waiting. The first
  automatic run is one full interval after the backend starts (six hours by
  default), not at start. It shares `allowance-sync.lock` with the CLI and
  the panel, so it never runs at the same time as them
| Portal backend

| `ALLOWANCE_SYNC_DISABLED`
| `true` stops the automatic allowance sync whatever the interval says.
  Admins can still preview and apply from Automations
| Portal backend

| `AAD_TENANT_ID`, `AAD_CLIENT_ID`
| Entra tenant and app client id used to validate MSAL idTokens
| Portal backend

| `PORTAL_URL`
| Public base URL of the portal, used in identity/OAuth redirect flows. The
  GitHub callbacks (App manifest and identity OAuth) are registered on its
  origin, so it may also point at a route such as `/settings`. Required in
  production: with `NODE_ENV=production` and no `PORTAL_URL`, the GitHub App
  manifest route refuses, because its URLs would fall back to localhost and
  be baked into the App
| Portal backend

| `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY_PATH`
| Optional. Not needed when an admin creates the GitHub App from Automations
  (the manifest flow stores its credentials under `ZAPLIE_DATA_DIR`). When
  both are set they win over the stored App key; set only one and it is
  ignored. See `docs/setup/zero-config-github.md`
| Portal backend

| `GITHUB_APP_SLUG`
| Optional. Overrides the stored App slug used for the "Connect repositories"
  install link
| Portal backend

| `GITHUB_OAUTH_CLIENT_ID`, `GITHUB_OAUTH_CLIENT_SECRET`
| Optional. Both or neither. When set, they must be the Zaplie GitHub App's
  own client ID and secret, not a separate OAuth App's, and that App must
  register `/api/identities/github/callback` on the `PORTAL_URL` origin.
  "Connect GitHub" uses them. When unset, the client of the App created from
  Automations is used
| Portal backend

| `GITHUB_OAUTH_REDIRECT_URI`
| Optional, and used only with the env OAuth client above. Defaults to
  `<PORTAL_URL origin>/api/identities/github/callback`, the callback the App
  manifest registers. The stored App client always uses the manifest callback
| Portal backend

| `TREASURY_USERNAME`
| LNbits account that owns the treasury wallet used by portal payouts
| Portal backend

| `IDENTITY_STATE_SECRET`
| HMAC key that signs the short-lived state token in the GitHub OAuth /
  identity-linking round trip (`backend/githubOAuthState.js`). If unset the
  backend generates one and persists it in `secrets.json`, so set it explicitly
  in production (`openssl rand -hex 32`) — otherwise in-flight links break
  whenever that file is lost or the app scales out.
| Portal backend

| `ZAPLIE_DATA_DIR`
| Durable directory for the mutable JSON stores, set on *both* App Services.
  REQUIRED in production: without it the stores sit inside the deployment tree
  and a clean deploy wipes them. The value depends on the App Service OS —
  `/home/data/zaplie` on Linux, `+D:\home\data\zaplie+` on Windows (the `home`
  share is the persistent one in both cases). `+%HOME%\data\zaplie+` is the
  portable spelling: the bot expands `%HOME%` itself, so one value is correct
  on either OS and on any stamp. Consumers: every portal backend
  store honours it (`data.json`, identities, connections, pending rewards,
  secrets, webhook keys, GitHub App credentials, the LNbits user directory);
  the bot's zap and reward ledgers (`bot-zap-ledger.json`,
  `bot-reward-ledger.json`) read it too, and outside
  explicit development mode the bot refuses to start without it. Set it on
  both — a component that does not read it yet simply ignores it.
| Bot, Portal backend

| `ZAPLIE_LEDGER_STALE_LOCK_MS`
| At startup, a ledger `.lock` file older than this many milliseconds is
  removed as crash-left (see <<Persistent application state>>). Default
  `30000` (30 seconds); `0` turns startup recovery off. A whole number of `0`
  or more: anything else makes the bot refuse to start. Raise it only for a
  share where a single ledger write can take seconds. Applies to the zap,
  reward and reward budget ledgers alike; nothing is ever evicted at runtime
| Bot

| `APPLICATIONINSIGHTS_CONNECTION_STRING`
| Connection string of the environment's Application Insights (`appi-zaplie`
  in `ka-zaplie-prod`, `appi-zaplie-test` in `ka-zaplie-test`). The bot sends
  its AgentActivity events (agent-pulse) there for the Agents Portal; unset,
  it emits nothing. Set by `infra/azure.bicep`; see <<Telemetry>>
| Bot

| `AGENT_ID`
| The Agents Portal id this deployment reports as: `zaplie` in production,
  `zaplie-test` in test (default `zaplie`). Set by `infra/azure.bicep` from
  its `agentId` parameter
| Bot

| `ZAPLIE_GUEST_ALLOWLIST`
| Guests (or users from other tenants) the bot may serve, besides members of
  its own tenant. Comma-separated: `person@example.com`, `@example.com` for a
  whole domain, or an Entra object id. Empty or unset (the default): members
  only. Anonymous meeting participants are never served. The portal backend
  reads the same setting for `POST /api/lnbits/users/me`
| Bot, Portal backend

| `FOUNDRY_PROJECT_ENDPOINT`, `FOUNDRY_MODEL`
| Azure AI Foundry project endpoint and model for the conversational
  assistant. Free text that matches no command in a 1:1 chat goes to the
  assistant only when both are set; otherwise the bot replies with the list
  of commands, as it does in group chats and channels. If the assistant
  fails (for example Foundry returns a server error after the SDK's
  retries), the bot says it can't chat right now and lists the commands,
  logs the error and starts a new Foundry conversation on the next message
| Bot

| `SCM_DO_BUILD_DURING_DEPLOYMENT`
| Must be `false`: CI ships a prebuilt artifact and Oryx must not rebuild it
| Portal (App Service setting)
|===

The portal App Service starts the Express backend with the startup command
`node backend/server.js`.

Secrets belong in `env/.env.*.user` files (gitignored) or Azure app settings —
never in tracked files.

`REACT_APP_*` is a public compile-time namespace, not a secret store. The
portal has no references to `REACT_APP_LNBITS_PASSWORD` or
`REACT_APP_LNBITS_ADMINKEY`; build workflows must not supply them.

[[Telemetry]]
== Telemetry (Agents Portal)

The bot reports what it does to the
https://agents.knowall.ai[Agents Portal] as `AgentActivity` custom events,
through the https://github.com/knowall-ai/agent-pulse[agent-pulse] library
(`src/services/pulse.ts`). Each environment has its own workspace-based
Application Insights, tagged `agent=<id>` so the portal finds it:

[cols="1,1,2"]
|===
| Agent id | Resource group | Resources

| `zaplie`
| `ka-zaplie-prod`
| `log-zaplie` (Log Analytics, 30 days), `appi-zaplie`

| `zaplie-test`
| `ka-zaplie-test`
| `log-zaplie-test` (Log Analytics, 30 days), `appi-zaplie-test`
|===

`infra/azure.bicep` declares both resources from its `agentId` parameter and
sets `APPLICATIONINSIGHTS_CONNECTION_STRING` and `AGENT_ID` on the bot.
`infra/azure.parameters.json` fills `agentId` from `AGENT_ID`, so
`teamsapp provision` needs `AGENT_ID=zaplie` (production) or
`AGENT_ID=zaplie-test` (test) in that environment's `env/.env.<env>` file. On an App
Service provisioned before that, set the two app settings by hand. In
production the bot App Service is `zaplie-prod-bot` in `ka-zaplie-prod` (the
Bot Service's messaging endpoint points at it):

[source,bash]
----
CS=$(az monitor app-insights component show -g ka-zaplie-prod -a appi-zaplie \
  --query connectionString -o tsv)
az webapp config appsettings set -g ka-zaplie-prod -n zaplie-prod-bot \
  --settings APPLICATIONINSIGHTS_CONNECTION_STRING="$CS" AGENT_ID=zaplie
----

For test, use `ka-zaplie-test`, `appi-zaplie-test`, the test bot App Service
and `AGENT_ID=zaplie-test`.

Events carry fixed titles and subjects, the zap amount as a `sats`
measurement and a SHA-256 of the upstream id — never a name, a zap message or
any other free text:

[cols="1,1,3"]
|===
| Type | Level | When

| `zap.sent` | success | A zap-card recipient is paid (subject `teams`) or an automation reward is paid (subject `automation`)
| `zap.failed` | error / warning | A zap fails before payment (error), its outcome cannot be confirmed (warning), or an automation reward fails (error)
| `zap.queued` | info | An automation reward waits for the recipient to connect a wallet
| `chat.answered` | success / info | A command ran (subject is the command), the assistant replied, or the command guide was shown
| `chat.failed` | error / warning | A message could not be handled (error) or was turned down with a reason (warning); the assistant failed and the command guide was sent instead (warning, subject `assistant-unavailable`); also the adapter's turn error handler
| `ledger.lock_timeout` | error | A ledger transition timed out waiting for the store's `.lock` (subject `ledger-lock`; channel `teams` for the zap ledger, `api` for the reward ledgers). Alert on it: until the lock is cleared every zap or reward fails (see <<Persistent application state>>)
|===

Telemetry is best effort: the library never throws and every call is wrapped,
so a telemetry outage cannot fail a zap or a reply.

== Day One

Complete these once per new environment, right after the first deployment:

. *Production's app registration is managed by hand. Read this first.* Do
  not run `teamsapp provision` (or anything else that applies
  `aad.manifest.json`) against the production Zaplie app. The manifest would
  rename the app and replace its roles, redirect URIs and token settings with
  the development values. Production's admin role id also differs from the
  manifest's (the `Zaplie.User` id matches), so applying it would drop the
  admin role people hold. In production, create and change roles in Entra
  directly (App registrations → the Zaplie app → App roles), using the same
  values as the manifest (`Zaplie.Admin`, `Zaplie.User`).
. *Create the app roles.* The roles are declared in `aad.manifest.json`.
  ** *Development and other provisioned environments:* they only materialise
     on the app registration after `teamsapp provision` runs again (the
     `aadApp/update` step applies the manifest), so re-run it once before
     looking for them.
  ** *Production:* create them by hand, as above. Don't provision. The same
     goes for the `acct` optional ID-token claim and the `/portal` SPA
     redirect URIs (https://github.com/knowall-ai/zaplie-bot/pull/488): add
     them in Entra (Token configuration, Authentication), not with
     `teamsapp provision`.
. *Check the sign-out landing is registered.* Confirm the production
  registration lists `https://<portal host>/login` (and the `/portal/login`
  URIs above) as single-page application redirect URIs; sign-out depends on
  it. Without it Entra ends a browser sign-out on its own page and the Teams
  sign-out popup never closes.
. *Assign the admin app role.* In Entra ID → Enterprise applications → the
  Zaplie app → "Users and groups", assign the admin role (value
  `Zaplie.Admin`; shown as "Zaplie Administrator" in provisioned
  environments and "Zaplie.Admin" in production) to at least one user. The
  portal's org-configuration endpoints reject every write until a signed-in
  user carries this role.
. *Restrict who can sign in to the portal.* Portal authentication accepts any
  account that can sign in to the tenant, guests included, and the portal is
  reachable directly in a browser, not only through the Teams tabs. Teams app
  availability (below) controls who can open the tabs; Entra controls who can
  sign in at all. Apply both:
  .. Grant tenant-wide admin consent first (App registrations → the Zaplie
     app → API permissions → "Grant admin consent", which covers the
     `User.Read` the portal requests). *Assignment required* turns off user
     consent for the app, so without it an assigned user who has never
     consented can't finish signing in
     (https://learn.microsoft.com/en-us/entra/identity-platform/howto-restrict-your-app-to-a-set-of-users#update-the-app-to-require-user-assignment[Microsoft]).
  .. In Enterprise applications → the Zaplie app → "Users and groups", assign
     the `Zaplie.User` role (no admin rights) to everyone who should use
     Zaplie, and the admin role (value `Zaplie.Admin`; shown as "Zaplie
     Administrator" in provisioned environments and "Zaplie.Admin" in
     production) to the admins. Use the role, not "Default Access": Entra
     refuses Default Access on an app that defines roles, and the portal UI
     would otherwise offer only the admin role.
  .. Only then set Properties → *Assignment required* to *Yes*. Anyone not
     assigned is refused at sign-in, except Global Administrators: Entra
     does not apply the assignment requirement to them
     (https://learn.microsoft.com/en-us/troubleshoot/entra/entra-id/app-integration/error-code-aadsts50105-user-not-assigned-role[AADSTS50105]).
     Keep that role to a few trusted accounts, and test the gate with an
     ordinary unassigned user, not an administrator.
  .. Keep this list in step with the Teams app's availability (below).
. *Prepare LNbits.* No extension is needed for provisioning: the bot creates
  users through the core Users API, which requires an LNbits admin account.
  Create the treasury wallet that funds automation rewards, fund it with one
  budget period at most, and copy its admin key into
  `REWARDS_TREASURY_ADMINKEY`. Then follow `docs/automation/README.md` to set
  `GITHUB_WEBHOOK_SECRET`, the reward amount, the budget and each repository
  webhook; nothing pays until the amount and the budget are set. Weekly
  allowances are paid by the LNbits
  https://github.com/BenGWeeks/allowance[allowance extension] from the Fund
  wallet, not by the bot; the portal keeps the schedules in step
  (*Automations → Weekly allowances*). Set `ALLOWANCE_FUND_ADMINKEY` and
  follow `docs/automation/README.md`, "Weekly allowances".
. *Rotate the burned LNbits credentials.* Historic CI builds injected
  `REACT_APP_LNBITS_PASSWORD` and `REACT_APP_LNBITS_ADMINKEY` into the
  portal's public JavaScript bundle, so any admin key or service-account
  password that ever reached a deployed environment must be treated as
  compromised. Rotate both in LNbits and update the server-side app settings
  (`LNBITS_PASSWORD`, `LNBITS_ADMINKEY`) — never reuse the old values.
. *Provisioning caveat.* A user's LNbits wallets are provisioned the first
  time the bot sees them (the Teams install event or their first message),
  so the tab cannot resolve a wallet for someone the bot has never seen.
  Only *members* of the bot's own tenant (`userRole` `user`, `tenantId` =
  `AAD_APP_TENANT_ID`) and guests listed in `ZAPLIE_GUEST_ALLOWLIST` are
  provisioned or answered. Anyone else (an unlisted guest, an anonymous
  meeting participant, an unlisted user from another tenant, or a sender
  Teams cannot resolve) gets no LNbits account, no reply and no error
  message (`src/services/memberGate.ts`).
. *Who can use the Teams app (Teams admin centre, Manage apps, Zaplie).*
  *Availability* decides who can use it, *Installs* who gets it without
  asking. "Everyone" includes the tenant's guests. External-access users
  (other organisations) can reach the bot only in supported group chats or
  meetings where the app is installed, and stay subject to
  `ZAPLIE_GUEST_ALLOWLIST`.
  Changing installs alone does not remove existing installs; availability
  is what blocks the app.
  ** *Members only (the default):* set both *Availability* and *Installs* to
     specific users or groups. Guests cannot use the app at all with that
     availability, even if they are assigned to it.
  ** *Members and some guests:* availability has to be *Everyone*, because
     no narrower setting reaches guests. The bot's allowlist is then the
     gate: add the guest's email, `@their-domain` or Entra object id to
     `ZAPLIE_GUEST_ALLOWLIST` on the bot's App Service and restart it.
     Guests not on the list can see the app but get no account and no reply.
     Keep *Installs* to the people who should get it automatically.
. *When an account is created.* A member or allowlisted guest is provisioned
  on the first turn the bot sees from them, which can be the Teams install
  event itself, not only their first message.

== Manifest and App Package

The manifest is localised: `manifest.template.json` declares English as the
default language and Spanish through `localizationInfo`, and
`appPackage/es.json` carries the Spanish name, descriptions and tab names.
`teamsApp/zipAppPackage` includes the file automatically. Command titles are
left in English on purpose: Teams inserts the title as the message text when
a user picks a command, and the bot matches those English words. Adding a
language means one more file and one more entry in `additionalLanguages`;
`npm run test:tooling` checks that every key in a language file points at a
real string in the template. That check reads the template, not the emitted
`appPackage/manifest.json`; this is enough because `build.js` only sets the
version, the URLs and the valid domains and passes `localizationInfo` through
unchanged.

The store listing (app name, descriptions, command descriptions and tab names,
English and Spanish) comes from the app package, not from the bot code. A
code-only deploy (the `deploy` stage of `teamsapp.yml`, which only zip-deploys
the App Service) changes the bot's replies but leaves the listing as it was: a
new or changed `es.json` reaches users only once the app package is rebuilt
and applied, through the `provision` or `publish` stage (both run
`teamsApp/zipAppPackage` and `teamsApp/update`) or an updated upload in the
Teams admin center. Until then a Spanish client sees the old, English listing
while the bot already answers in Spanish.

`build.js` (`npm run build-manifest`) substitutes `CONTENT_URL`/`WEBSITE_URL`
into `manifest.template.json`, takes the version from `APP_VERSION` when set
(otherwise the template version, with the patch auto-incremented for
Test/Prod), and writes `appPackage/manifest.json` (gitignored). The manifest
declares the bot (personal/team/groupchat scopes with the four commands) and
five static tabs (Feed, Users, Rewards, Wallet, Settings).
