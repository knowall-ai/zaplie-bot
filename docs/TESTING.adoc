== Overview

Testing is currently unit-test only: Jest in the bot and the tabs app, and
Node's built-in `node:test` for the tabs backend. There is no end-to-end or
integration test suite yet; the Azure Functions have no tests. This document records the current state and the strategy for
closing the gaps.

== Test Types

=== Unit Tests — Bot (repo root)

- Framework: Jest 29 with `ts-jest`, coverage floors, and a checked-in coverage
  ratchet baseline.
- `src/services/zapLedger.test.ts` covers restart durability, independent
  instances, two actual Node processes, exclusive-lock timeout after a crash,
  atomic-write crash leftovers, strict schema/config validation, key scoping,
  and the absence of raw Teams and wallet identifiers from the store.
- `src/commands/zapRecipient.test.ts` exercises the production transition path,
  including safe pre-payment release, persisted unknown outcomes, and a paid
  duplicate after restart that never invokes the payment dependency.
- `src/services/recipientNotifier.test.ts` drives the notifier through a
  stand-in adapter that mimics the real pipeline (an error leaving the callback,
  or thrown by a middleware before it, goes to `onTurnError`), so a refused
  or never-attempted send is reported as a failure and never as a delivery;
  `src/commands/zapRecipient.test.ts` pins that the `onPaid` step runs only
  after the ledger records the payment and cannot change the outcome;
  `src/teamsBot.test.ts` pins that the chat is opened after the receipt;
  `src/services/fetchUserMiddleware.proactive.test.ts` pins that the
  synthetic proactive event skips the Teams and LNbits lookups.
- `src/services/rewardLedger.test.ts` covers the reward idempotency ledger:
  reserve, replay of each state, fingerprint conflicts, release of only a
  `processing` record, restart durability, ten concurrent reserves acquiring
  exactly once, pruning of settled records only, the lock-timeout message,
  and strict schema and key validation.
- `src/rewardsRoute.test.ts` drives `POST /api/v1/rewards` over HTTP against a
  real ledger in a temporary directory and the real `payReward`, with LNbits
  and the portal stubbed. It pins that a redelivery, a concurrent duplicate, a
  restart, or an unknown payment outcome never calls `payInvoice` twice; that
  a pending-reward write with an unknown outcome is held and never queued
  again; that a failure known to have taken no effect releases the key so a
  retry pays; that a reused key for a different reward is a `409`; and that a
  missing or malformed `Idempotency-Key` or a bad API key never reaches the
  ledger.
- The `payReward` blocks in `src/services/rewardsService.test.ts` and
  `src/services/identityService.test.ts`, with
  `src/services/pendingRewardsService.test.ts`, pin which failures are a
  `RewardPaymentUncertainError`: a `payInvoice` failure or missing payment
  hash, or a pending-reward request that failed in flight or got a 5xx. A 4xx
  from the portal, or anything before the request, stays a plain error.
- The `TeamsBot free text in a 1:1 chat` block in `src/teamsBot.test.ts` pins
  that unmatched 1:1 text gets the command guide, never the assistant or an
  error, unless both `FOUNDRY_PROJECT_ENDPOINT` and `FOUNDRY_MODEL` are set.
  It also pins that when the assistant fails (for example a Foundry
  `server_error`), the user gets "I can't chat right now" and the command
  list instead of the generic error, the failure is logged, and the next
  message starts a new Foundry conversation. The `TeamsBot records
  AgentActivity events` block pins that such a failure is recorded as
  `chat.failed` at warning level, with no `chat.answered`.
- `src/services/lnbitsService.test.ts` mocks `fetch` and exercises the real
  service logic for wallet, invoice, and payment calls.
- `src/i18n/i18n.test.ts` pins language resolution and rendering (Spanish
  for `es-*`, English otherwise, placeholder parity, fallback with a warning,
  a missing parameter left visible with a warning) and `formatNumber`
  (`es-ES` writes `10.000`, `es-MX`/`es-419` `10,000`, anything else English,
  never the server locale). `src/teamsBot.i18n.test.ts`,
  `src/onTurnError.test.ts`, `src/commands/showMyBalanceCommand.i18n.test.ts`
  and the language blocks in the leaderboard, calendar and zap command tests
  assert Spanish replies through the handlers; `src/teamsBot.i18n.test.ts`
  runs every registered command for an `es-MX` client and fails on any
  English copy. `src/services/foundryAgentService.test.ts` pins that every
  turn carries a reply-language hint on its input (Spanish for a Spanish
  client, an English counter-hint otherwise), that an English turn after a
  Spanish one in the same conversation overrides the stored Spanish hint, and
  that switching language never re-creates the agent.
- `src/services/paymentExtra.test.ts` and the `SendZap payment metadata` block
  in `src/commands/sendZapCommand.test.ts` pin the keyless payment metadata
  projection (no wallet keys or balances in LNbits `extra`).
- Run:

[source,bash]
----
npm test
npm run test:coverage
npm run coverage:ratchet
----

=== Unit Tests — Web Tabs (`tabs/`)

- Framework: Jest via react-scripts, with React Testing Library and jest-dom
- Test files: `tabs/src/services/lnbits/*.test.ts` (mock global `fetch` and
  localStorage; cover `getAccessToken`, `getWallets`, `getWalletBalance`,
  `getUserWallets`, `createInvoice`, `payInvoice`),
  `tabs/src/setupTests.test.tsx` (environment smoke test) and the component
  suites under `tabs/src/components/`. Among them,
  `AutomationsComponent.test.tsx` covers the GitHub App setup block (create
  with or without an organisation, the created and env states, gating
  "Connect repositories", the `?setup=` toasts), and
  `ConnectionsSetting.test.tsx` covers the `?github=` returns from the
  identity and install flows
- Run:

[source,bash]
----
cd tabs
CI=true npm test -- --watchAll=false   # one-shot
npm test                               # watch mode
----

=== Unit Tests — Web Tabs backend (`tabs/backend/`)

- Framework: Node's built-in `node:test` runner with `node:assert/strict`; no
  extra dependencies
- Test files: `tabs/backend/*.test.js` (auth middleware, config routes, rate
  limiting, reward amounts, automation payments, LNbits user directory, SPA
  fallback route). The GitHub App suites:
** `githubAppConfig.test.js`: env-over-stored precedence per group, the
   redirect URI, readiness, corrupt-store and malformed-`PORTAL_URL`
   handling, and the documented 409 wording.
** `githubAppAuth.test.js`: App JWT signing with the stored or env key.
** `githubOAuthState.test.js`: the purpose-tagged states (identity, install,
   each with the oid and a browser binding hash) never pass as one another or
   as the plain state, and a wrong field count is refused.
** `githubRoutes.test.js`: the GitHub routes before and after the manifest
   flow stores credentials, the manifest's organisation target and its
   validation, status `source` and `installationReady`, and bad config.
** `githubSetupFlow.test.js`: the whole zero-config path with no `GITHUB_*`
   env vars, with GitHub and LNbits stubbed at `fetch`. It covers manifest
   conversion (including the stored owner login), the install link, and the
   setup URL's App-JWT check: `GET /app/installations/{id}` with the
   account matched to the App owner, and no user sign-in. It then covers
   listing repositories with the stored key, identity linking with the
   stored OAuth client, and the identity resolution the reward flow uses.
   Each simulated browser keeps its own cookie jar: the install and identity
   links set the binding cookie (`HttpOnly`, `Secure`, `SameSite=Lax`, its
   path, `Max-Age=600`) and the callbacks clear it. A link opened in another
   browser, with no cookie or another flow's cookie, records nothing and
   makes no GitHub call.
   Rejections cover an installation on another account, a 404, a GitHub
   error, forged and crossed states, and non-numeric or non-canonical ids.
   An env-configured App takes its owner from `GET /app`, cached, and the
   identity user token never reaches disk or logs.
- `server.js` only calls `listen()` when run directly, so each test file can
  `require('./server')` and bind an ephemeral port
- Needs no credentials: each file that loads the server sets placeholder
  `TAB_BACKEND_TOKEN`, `AAD_TENANT_ID` and `AAD_CLIENT_ID` values first; the
  pure-module tests need nothing
- Runs in CI as the "Run backend tests" step of the
  "Unit Tests (Frontend/Tabs)" job
- Run:

[source,bash]
----
cd tabs
npm run test:backend
----

=== Azure Functions (`functions/`)

No automated tests yet (`npm test` prints "No tests yet"). The Postman
collection in `Postman/` supports manual API testing of `getUsers`,
`showUsers`, and `sendZap`.

=== End-to-End Tests

Not yet implemented. The intended approach is Playwright scripts driven by the
scenarios in `docs/requirements.yaml`, which catalogues the features
(feed statistics, leaderboard, SSO auth, rewards carousel, allowance,
transaction history, send/receive payment, Zap notifications, user list) as
Given/When/Then acceptance scenarios.

== Requirements Traceability

`docs/requirements.yaml` is the requirements catalogue for the Copilot MVP:
each feature lists deliverables, user stories, and Given/When/Then scenarios.
New E2E tests should reference the feature `id` (e.g. `total-zaps`,
`leaderboard`, `sso-auth`) so coverage can be traced back to requirements.

== Manual Testing

- *Bot:* sideload the app via Teams Toolkit (`teamsapp preview --env local`)
  with a dev tunnel on port 3978; exercise `send zap`, `show my balance`,
  `show leaderboard`.
- *Bot Zap retries:* use a controlled non-production wallet and a durable test
  data directory. Submit one card twice and confirm only one LNbits payment.
  Restart the bot and submit the same card again; it must remain blocked. For a
  crash exercise, stop after `processing` is durable and confirm the restarted
  bot does not call LNbits for that recipient. Reconcile LNbits before any
  record or orphan-lock repair; do not delete a barrier merely to retry.
- *Automation reward retries:* with the same setup, send one reward request
  twice with the same `Idempotency-Key` (see the smoke test in
  `docs/automation/README.md`). The second response must match the first,
  carry `Idempotency-Replayed: true`, and LNbits must show one payment. Then
  redeliver a merged-PR webhook from GitHub's webhook settings and confirm the
  Logic App run gets the replayed result.
- *Tabs:* `cd tabs && npm start` (Express backend on 5000, CRA dev server on
  3000) and verify Feed, Users, Rewards, Wallet, and Settings against a dev
  LNbits instance.
- *Functions:* `cd functions && npm start` with the Postman collection.
